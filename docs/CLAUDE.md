# CLAUDE.md — Padaraksha Factory Management System

## Project Overview

**Padaraksha** is a factory management web application for a footwear (sandal) manufacturing business. The factory receives raw materials from provider companies, manufactures sandals, and sends finished goods back to them. The app manages the full production lifecycle: material receipt → production → quality check → outward delivery → payroll.

**Tech Stack:**
- Backend: Python FastAPI
- Database: MySQL
- Frontend: React / Next.js
- Design: Desktop-first, responsive for mobile

---

## Business Context

### Factory Model
- The business operates **multiple factory locations** (currently 2), each as a **separate legal entity** with its own GST number, articles, and staff.
- A single user selects which factory they're logging into at the login screen.
- One factory can serve **multiple provider companies** simultaneously.
- An **Article** (sandal design) is defined globally but linked to specific provider companies via Purchase Orders. The same article can be produced for multiple providers — BOM is identical across providers.

### Key Business Rules
1. **5-Day Incentive Rule**: A percentage incentive is earned per PO if finished goods are delivered back to the provider within 5 days of the PO arrival date. Provider-side delays (late department bills) do not affect eligibility. Track this per PO.
2. **Quality Incentive**: A separate quality-based percentage incentive per PO. Exact percentage TBD — app should track quality score per PO for future calculation.
3. **Rework is Unpaid**: When a worker's piece is rejected in QC (internal or provider-side), the rework goes back to the worker who caused the defect. This rework is logged but **does not count toward pay**.
4. **Damage Deductions**: If factory damages raw materials, the cost is deducted from receivables (not paid upfront). Track as a financial loss/expense record.
5. **Partial Shipments**: Outward deliveries can be partial. Providers may reject and return only failed pieces, or the entire shipment if failures are too high.

## Module Specifications

---

### 1. Authentication & Factory Selection

**Flow:**
- User opens app → sees list of registered factory locations → selects one → enters credentials → lands on that factory's dashboard.
- All data (articles, staff, POs, production records) is scoped to the selected factory.

**Roles:**
- **Admin (Owner)**: Full access to all modules and settings.
- **Supervisor**: Access controlled by Admin. Admin can toggle which modules/actions a supervisor can access.
- No worker-facing app access currently.

**DB Tables:** `factories`, `users`, `roles`, `permissions`

---

### 2. Dashboard

**Purpose:** Central hub for quick actions and daily snapshot.

**Top 3 Daily Reports (shown on dashboard):**
1. Workers present today + their productivity (pieces completed)
2. Inventory status (current stock of each raw material)
3. Damages and repairs from our production

**Quick Action Buttons:** New Inward Entry, Assign Work, Internal QC, New Outward Delivery

---

### 3. Article Management

**What an Article is:**
- A sandal design identified by an article number/name.
- Defined once globally; linked to provider companies via POs.

**Article Properties:**
- Article Number / Name
- Colour
- Size
- Gender (Men / Women / Kids / Unisex)
- Left / Right (or Pair)

**Bill of Materials (BOM):**
- List of raw materials needed (e.g., insole, lace, upper, thread, gum)
- Quantity per piece for each material
- BOM is the same across all size/colour variants of an article
- BOM can be updated mid-production if process is upgraded

**Work Process:**
- List of work stages defined per article (e.g., cutting, stitching, sole fixing)
- Each stage has: stage name, sequence order (can be parallel for early stages), and a pay rate per piece
- Sequence is flexible — some early stages can run in parallel, later stages are sequential
- Work process can be updated mid-production (process upgrade / machinery change)
- No system enforcement of stage order — record freely

**DB Tables:** `articles`, `article_variants`, `bom_items`, `raw_materials`, `work_stages`

---

### 4. Inward Entry (Material Receipt)

**Trigger:** Provider company sends raw materials to factory with a Purchase Order.

**Purchase Order (PO):**
- Generated by provider's head office
- Contains: PO number, date, list of raw materials, quantity of each, price per item
- Prices are for reference/dispute purposes and damage deduction calculation
- 5-day incentive clock starts on PO arrival date

**Department Dispatch Bills:**
- Materials come from multiple departments of the provider (e.g., Insole Dept, Upper Dept)
- Each dept sends a separate small dispatch bill with its own bill number, linked to the main PO
- Bills may arrive on the same day as PO or a few days later
- Each bill shows: item, quantity dispatched, whether full or short
- Shortages from departments = provider's responsibility, flagged in system

**Inward Entry Flow:**
1. Select factory
2. Enter / select PO number + arrival date
3. Link to provider company
4. Select article variants covered by this PO
5. For each raw material in BOM: enter expected qty (from PO) and actual qty received
6. For each department dispatch bill: enter bill number, department name, items, qty dispatched, qty short
7. System flags any shortage as provider's liability
8. System shows 5-day deadline for this PO

**DB Tables:** `purchase_orders`, `po_line_items`, `inward_entries`, `department_bills`, `dept_bill_items`

---

### 5. Inventory

**Purpose:** Real-time view of raw material stock.

**Stock is calculated as:**
`Received (inward entries) − Consumed (assigned to production) − Damaged`

**Features:**
- Current stock of each raw material
- History of receipts and consumption
- Low stock visibility
- Damage log (separate from consumption)

**DB Tables:** `inventory`, `inventory_transactions`

---

### 6. Raw Material Repurchase (Damage Recovery)

**Triggered when:** Factory damages a raw material and must repurchase it from the provider.

**Tracking fields:**
- Order date
- Item(s) ordered + quantity
- Provider / department ordered from
- Expected delivery date
- Actual arrival date
- Days taken since order
- Outstanding / pending items
- Cost (at PO reference price) — logged as factory expense/loss

**This is separate from Inward Entry** — it's a damage-recovery purchase, not a production order.

**DB Tables:** `damage_repurchases`, `damage_repurchase_items`

---

### 7. Production Tracking

**Assignment:**
- Supervisor opens Production Assignment screen
- Selects: Article → Work Stage → Worker(s) → Quantity → Start Date/Time
- Multiple workers can be assigned to the same stage (either split quantity or joint)
- One entry = one task assignment (not per piece — e.g., "Ramesh — Stitching — 50 pieces — Article X")

**Work Entry:**
- When work is completed: log end date/time and actual quantity completed
- System records: worker, article, stage, qty assigned, qty completed, start time, end time

**Pay Eligibility:**
- Only original (non-rework) completions count toward pay
- Rework completions are logged separately with a `is_rework: true` flag

**DB Tables:** `work_assignments`, `work_completions`

---

### 8. Internal Quality Check (QC)

**Performed by:** Dedicated QC staff or supervisor.

**Flow:**
1. Select article / batch / work stage
2. Enter: total pieces inspected, passed qty, failed qty
3. For failed pieces: identify which work stage caused the defect
4. System looks up who did that stage for that batch → assigns rework to that worker
5. Rework assignment is logged with `is_rework: true` (no pay)
6. A piece can be sent for rework multiple times

**DB Tables:** `qc_inspections`, `qc_failures`, `rework_assignments`

---

### 9. Outward Delivery

**Flow:**
1. Select PO / article / batch
2. Enter: total pieces dispatched, shortage (not produced), spoiled (damaged beyond repair)
3. Partial shipments allowed — can send multiple outward entries against same PO
4. System tracks: promised qty vs. dispatched qty vs. shortages vs. spoiled
5. Spoiled pieces = factory expense, logged for loss tracking

**Provider QC Response:**
- Provider may reject and return: only failed pieces OR entire shipment
- When return arrives: log return receipt, qty returned, reason
- Failed pieces go back to original worker for rework (unpaid)
- If high failure rate: log full return, reassign all for rework

**DB Tables:** `outward_deliveries`, `outward_line_items`, `provider_returns`, `provider_qc_failures`

---

### 10. Payroll & Employee Management

**Employee Record:**
- Name, role, factory location, join date, pay type (fixed / piece-rate / hybrid)
- Fixed wage amount (monthly)
- Piece rates are per work stage (defined in Article → Work Stage)

**Pay Types:**
- **Fixed**: Daily/monthly wage for standard 8-hour day
- **Piece Rate**: Paid per piece completed
- **Hybrid**: Fixed wage for first 8 hours; piece rate for any work done beyond 8 hours in a day

**Deductions:**
- Advances taken
- Fines
- Absences (for fixed/hybrid workers)
- PF / ESI (if applicable)
- Material damage costs (if attributed to worker)

**Payroll Calculation:**
- Admin selects date range (daily to monthly — free choice)
- System aggregates: pieces completed (non-rework only), hours worked, deductions
- Shows breakdown per worker: gross pay, deductions, net pay
- Rework quantities are shown as a separate column (unpaid)

**Attendance:**
- Daily attendance log per worker (present / absent / half-day)

**DB Tables:** `employees`, `attendance`, `payroll_runs`, `payroll_line_items`, `advances`, `deductions`

---

### 11. Reports

**Priority Reports:**
1. **Daily Worker Report**: Who is present, tasks done today, pieces completed, productivity vs. capacity
2. **Inventory Report**: Current stock of all raw materials, daily consumption, receipts
3. **Damage & Repair Report**: Pieces damaged in production, rework sent, spoiled goods, financial loss

**Other Reports:**
- PO Status Report: open POs, 5-day deadline countdown, incentive eligibility
- Article Production Report: by article, by period — total produced, defect rate, completion time
- Worker Payroll Report: earnings, deductions, rework log per worker per period
- Provider Shortage Report: dept bill shortages by provider, pending dues
- Outward Delivery Report: shipped vs. promised vs. spoiled per PO

## Data Architecture Summary

### Key Relationships
```
Factory → Users, Articles, Employees, POs, Inventory

Provider Company → POs → Inward Entries → Dept Bills
                       → Outward Deliveries → Provider Returns

Article → BOM Items (raw materials)
        → Work Stages (with pay rates)
        → Article Variants (colour, size, gender, L/R)

PO → Article Variants → Work Assignments → Work Completions
                     → QC Inspections → Rework Assignments
                     → Outward Deliveries

Employee → Work Assignments → Payroll
         → Attendance
         → Advances / Deductions
```

## UI/UX Guidelines

### Design Principles
- **Simple and productive**: Minimize clicks to enter data. Forms should be pre-filled where possible.
- **Desktop-first**: Primary use is on desktop/laptop in a factory office. Must also work on mobile.
- **Elegant minimalism**: Clean, uncluttered interface. No unnecessary decoration.
- **Quick actions**: The most common daily tasks (inward entry, assign work, QC, outward) must be reachable in 1–2 clicks from dashboard.

### Visual Design Direction
- **Palette**: Deep slate navy (`#1E2A3A`) as primary, warm white (`#F8F7F4`) background, muted amber (`#C9973A`) accent for actions and highlights, soft gray (`#6B7685`) for secondary text. Inspired by the raw materials and craft of the trade — leather, thread, earth.
- **Typography**: A clean geometric sans-serif (e.g., Inter or DM Sans) for UI text. Slightly heavier weight for data fields to improve scanability. No display fonts.
- **Layout**: Sidebar navigation (collapsible on mobile), content area with clear section headers, data-dense tables where needed.
- **Forms**: Inline editing where possible. Dropdowns with search. Auto-fill from previous entries.
- **Status indicators**: Color-coded pills for PO status (open / in-progress / delivered / overdue), QC status (passed / failed / rework), worker status.

### Key UX Patterns
- **Inward Entry**: Wizard-style multi-step form (PO details → material quantities → dept bills → confirm).
- **Production Assignment**: Quick-add card — article search, stage select, worker select, quantity — minimal fields visible.
- **QC Entry**: Table format — list of pieces, pass/fail toggle per row, bulk actions.
- **Dashboard**: 3 daily snapshot cards (attendance, inventory, damages) + quick action buttons + PO deadline alerts.

## Development Notes

### Multi-tenancy
- All queries scoped by `factory_id`
- User sessions carry `factory_id` after login
- Permissions are `user_id × factory_id × module × action`

### Incentive Tracking
- Store `po_arrival_date` on every PO
- Compute `days_since_arrival` in real time
- Flag POs crossing 5 days as `incentive_at_risk`
- Store `quality_score` per PO (percentage, nullable until known)

### Rework Flag
- All work assignment records have `is_rework: boolean`
- Payroll queries filter `WHERE is_rework = false` for pay calculation
- Reports show rework separately

### Piece Tracking
- No physical piece IDs — all tracking is by count per assignment
- QC failures are counts, not individual piece records

### Article Versioning
- BOM and work stage changes mid-production should be logged with a timestamp
- Keep history of changes for audit purposes

- Automated billing / invoicing to providers
- Multi-currency support
- Barcode / RFID scanning
- Raw material purchasing from third-party suppliers (only provider repurchase covered)
